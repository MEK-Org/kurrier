Kurrier can be self-hosted on any modern Linux, macOS, or ARM device (including Raspberry Pi).
It’s distributed as a Docker setup for convenience, but you can also run it manually from source if you prefer.

> 🧱 **Kurrier’s core stack:**
> Next.js + Nitro (API worker) + Postgres + Redis + IMAP/SMTP connectors

---

## Prerequisites

Before you start, make sure you have:

- **Docker** and **Docker Compose** installed
→ [Install Docker](https://docs.docker.com/get-docker/)
- **Git** (for cloning the repository)
- **At least 1 GB RAM** and **1 vCPU**  (2 GB+ recommended for production)
- Optional: a domain name (for `mail.yourdomain.com` or similar)

---

## Quick start (Docker)

Clone the repository and copy the example environment file:


```bash
git clone --single-branch https://github.com/kurrier-org/kurrier.git
cd kurrier/db
# For new installations, copy the example environment file.
# If updating or cutting over from an existing deployment, preserve your existing .env!
cp -n example.env .env || true
docker compose up -d
```

Open the `.env` file and update your secrets and passwords. If you have an existing `.env` from a preview installation, keep your existing keys (such as `JWT_SECRET` and `APP_SECRET_ENCRYPTION_KEY`) intact. You can also use the built-in secrets generator below to create secure passwords and secrets.

```bash
JWT_SECRET=replace_with_your_jwt_secret_key
APP_SECRET_ENCRYPTION_KEY=replace_with_your_app_secret_encryption_key
```

<Callout type="info">
    **Deterministic Bootstrap & Private Port Bindings**:
    Kurrier's Compose configuration automatically coordinates startup: `postgres` initializes its healthcheck, `migrate` runs all database migrations and applies role passwords, and only then do `web` and `worker` launch. Backing infrastructure services (Postgres, Redis, Typesense, Garage S3, and Baikal) are bound to `127.0.0.1` so they are never exposed to the public internet.
</Callout>

## 🧩 Local vs. Hosted Setup

Kurrier can run in **two modes** — local and hosted (on a VPS etc with a domain name).
Both work the same way, but differ in how external services like **AWS SES**, **SendGrid**, or **Mailgun** can reach your server.

### 🖥️ Local Setup

If you’re running Kurrier on your own laptop or private machine (http://localhost or internal IP),
email providers can’t reach your API directly to deliver incoming messages or webhooks.

To solve this, Kurrier allows you to define your own public tunnel URL via any tunneling service such as [ngrok](https://ngrok.com/docs/getting-started), [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-apps/), or [LocalTunnel](https://github.com/localtunnel/localtunnel).

Example using ngrok:

```bash
  ngrok http <port>
```

You can also use any other tunneling service of your choice.

Update your `.env` file with the generated public URL:

```bash
LOCAL_TUNNEL_URL=https://your-ngrok-tunnel-url.ngrok-free.app
```

<Callout type="warning">
    We highly recommend hosting Kurrier on a public server with a domain for production use as tunnels might not be reliable for production workloads
    and any downtime or change in the tunnel URL will break incoming email delivery and webhooks.
</Callout>


### 🖥️ Hosted Setup

When hosting Kurrier on a server or cloud instance (e.g. DigitalOcean, AWS, Hetzner, or your own VPS),
you should use your own domain and disable tunneling by removing or commenting out the `LOCAL_TUNNEL_URL` variable in your `.env` file.

```bash
WEB_URL=https://www.yourdomain.com
```

<Callout type="warning">
    `DAV_URL` also needs to be a publicly reachable address — it's the CalDAV/CardDAV
    connection URL shown on the Sync Services page for configuring external clients
    (Thunderbird, iOS, Android, etc). The default (`http://localhost:5232`) only works
    for local setups. For a hosted deployment, set it to your own domain/port or a
    reverse-proxied path, e.g. `DAV_URL=https://dav.yourdomain.com`.
</Callout>

### Optional: hide Kurrier Drive

If your organization uses a separate file platform, such as Nextcloud, you can
hide Kurrier Drive and its storage-management UI:

```bash
DISABLE_DRIVE=true
```

Restart the web container after changing this value. This setting only disables
Kurrier's Drive web interface. It does not disable the object storage used for
email, raw EML files, or attachments, and it does not delete existing Drive
data. Set the value back to `false` and restart the web container to restore the
Drive interface.

### Optional: disable local login

For SSO-only deployments, you can hide the email/password login form and reject
local login attempts server-side:

```bash
DISABLE_LOCAL_LOGIN=true
```

Configure at least one Google or generic OIDC provider before enabling this
option. Otherwise, the login page will report that no login methods are
available. Restart the web container after changing the value.

This setting does not change signup availability. Use `DISABLE_SIGNUP=true`
separately when local account registration should also be disabled.

---

✅ Once you are all set with your environment variables you are now ready to run

```bash
docker compose up -d
```

✅ To stop Kurrier, run

```bash
docker compose down
```

### 🩺 Health Checks and Verification

To verify that the full stack and migration bootstrap initialized correctly:

1. Check running container status:
   ```bash
   docker compose ps
   ```
   All services (`postgres`, `redis`, `typesense`, `garage`, `baikal-postgres`, `dav`, `web`, `worker`) should show as running/healthy, and `migrate` should show as `Exited (0)`.

2. Confirm database migration success:
   ```bash
   docker compose logs migrate
   ```
   Should conclude with:
   `✅ All migrations done.`
   `✅ Bootstrap complete.`

3. Check Postgres connection:
   ```bash
   docker compose exec postgres pg_isready -U postgres -d postgres
   ```

4. Check Redis responsiveness:
   ```bash
   REDIS_PW=$(grep -E '^REDIS_PASSWORD=' .env | head -n1 | cut -d= -f2- | tr -d '\r"')
   docker compose exec redis redis-cli -a "$REDIS_PW" ping
   ```
   Expected response: `PONG`.

5. Check Web UI HTTP status:
   ```bash
   curl -fsS -o /dev/null -w "%{http_code}\n" http://localhost:3000/auth/login
   ```
   Expected response: `200`.

6. Check Worker API proxy connectivity:
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/api/kurrier/me
   ```
   Expected response: `401` (Unauthorized: confirms Next.js is actively proxying API routes to the worker).
